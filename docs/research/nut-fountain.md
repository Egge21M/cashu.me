# nut-fountain feasibility for Cashu.me

Initially assessed 2026-10-06 against the published `nut-fountain@0.1.0` tarball and the Cashu.me checkout. The initial assessment made no implementation changes; the subsequently approved implementation is recorded below. No existing research directory was present, so this note lives in `docs/research/`.

## Implementation follow-up

Implemented after the assessment was approved:

- Animated token display defaults to 256 total binary bytes and 20 FPS. The controls offer 128/256/512 bytes and 5/10/20 FPS. An explicit UR compatibility option retains outgoing support for older wallets. UR sizes refer to source fragment bytes, not total encoded QR bytes.
- `TokenQrCode.vue` renders explicit byte segments with the existing `qrcode` dependency. Small tokens still use static text QR codes; long single-proof tokens animate as well.
- `QrcodeReader.vue` uses ZXing's supported `textMode: "Hex"` to recover raw bytes losslessly through the existing text-only scanner wrapper, avoiding a fork. The scanner allows up to 30 scans/second. A bundled worker configures its own local WASM URL; the package's main-thread WASM configuration does not propagate to its worker. Vite 2 emits the worker as an ESM entry through a small virtual-module plugin because it does not support `?worker&url`. The scanner is kept outside Vue reactivity so its options remain cloneable across the worker boundary. `TokenQrDecoder` routes fountain/UR frames, retains legacy token text, and passes ordinary invoices and URLs through.
- Invalid or foreign frames leave valid transfer progress intact. A Restart scan control resets the transfer. Completion stops scanning and emits once. Animation stops on token changes and unmount; speed changes preserve the encoder sequence.
- `nut-fountain` is pinned to 0.1.0. The wallet's direct cashu-ts remains locked to 4.9.0; nut-fountain installs its required 4.11.0 separately.
- Validation: 293 Vitest tests pass (including 19 new QR transport/component tests), repository lint and changed-file formatting checks pass, and production SPA and PWA builds succeed. The generated PWA service worker precaches the scanner worker and ZXing WASM assets. Binary PNG round trips use the actual ZXing decoder and the same Hex conversion as the camera path. Physical-camera throughput on Android/iOS remains to be measured.
- A Chromium smoke test mounted the actual renderer and reader, fed a canvas camera stream at 20 FPS, and reconstructed a synthetic 24-proof token through both fountain and UR, plus a static invoice. This exercised the real scanner worker and local WASM decoder, without contacting a mint. These synthetic-camera checks do not establish physical-camera reliability.

The sections below retain the original assessment and its compatibility constraints.

## Conclusion

Replacement is technically feasible, but requires adapting the QR renderer and scanner to preserve binary bytes. It is not a dependency-only substitution. Existing incoming Cashu.me UR transfers can remain supported through `AutoDecoder`; new outgoing fountain frames use a different, experimental protocol that UR-only wallets cannot read. The package does not provide a UR encoder. Current NUT-16 still specifies UR for animated token transfers. [Package documentation](https://github.com/Egge21M/nut-fountain/tree/c18459671c0412dd3be0192f4b45e689d545cffb/packages/nut-fountain), [NUT-16](https://github.com/cashubtc/nuts/blob/main/16.md).

## Requested defaults

| Requirement | Implementation setting | Consequence |
| --- | --- | --- |
| 256 total binary bytes per QR code | `new FountainEncoder(message, { fragmentSize: 232 })` | Each frame has 232 fragment bytes plus 24 framing/checksum bytes. |
| 256 fragment payload bytes | `fragmentSize: 256` | Produces **280 total binary bytes** per QR code. |
| 20 displayed frames per second | Application interval of `50` milliseconds | The package has no animation scheduler or FPS setting. |

For the literal requirement “256 bytes per code,” use `fragmentSize: 232`; QR symbol encoding and error-correction overhead are additional. The package's own fragment default is 128, so either interpretation requires an explicit override. The application's scanner also defaults to 15 scans/second and should be configured for at least 20; this is a maximum processing cadence, not a guarantee every frame is captured. [Frame layout and bounds](https://github.com/Egge21M/nut-fountain/blob/c18459671c0412dd3be0192f4b45e689d545cffb/packages/nut-fountain/docs/protocol.md#4-frame-layout), [application responsibilities](https://github.com/Egge21M/nut-fountain/blob/c18459671c0412dd3be0192f4b45e689d545cffb/packages/nut-fountain/docs/implementation.md#costs-limits-and-transport-responsibilities), [scanner source](https://github.com/MakePrisms/qr-scanner).

## Integration points

1. `src/components/DisplayTokenComponent.vue` currently creates `UR.fromBuffer(Buffer.from(tokenText))`, calls `UREncoder.nextPart()`, and renders strings through `vue-qrcode`. Replace the animated transport with `FountainEncoder.nextFrame()` and render the returned `Uint8Array` as an explicit QR byte segment. The installed `@chenfengyuan/vue-qrcode@2.0.0` declares a string value prop and calls `String(this.value)`, so passing bytes or segments directly is insufficient. A small canvas component can call the already-declared `qrcode` library with `[{ data: frame, mode: "byte" }]`. Preserve static token QR handling. Current animation defaults are 150 fragment bytes and a 150 ms interval; controls need consistent revised presets. [Published renderer package](https://registry.npmjs.org/@chenfengyuan/vue-qrcode/2.0.0), [qrcode binary data API](https://github.com/soldair/node-qrcode#binary-data).
2. `src/components/QrcodeReader.vue` currently receives a `ScanResult` with `data: string`. The installed scanner version, `@agicash/qr-scanner@0.1.2`, discards ZXing's raw bytes and exposes decoded text. Its worker/main-thread result mapping must expose raw bytes, or this scanner path must use a byte-preserving scanner. Re-encoding its text into bytes is not reliable for arbitrary binary frames. [Scanner source](https://github.com/MakePrisms/qr-scanner), [binary-input requirements](https://github.com/Egge21M/nut-fountain/blob/c18459671c0412dd3be0192f4b45e689d545cffb/packages/nut-fountain/docs/implementation.md#automatic-format-routing).
3. Route binary fountain bytes and `ur:` inputs to `AutoDecoder`. Keep ordinary text results on the existing path: the decoder does **not** recognize bare tokens, invoices, URLs, or base64-wrapped fountain frames. Use `decoder.progress` for the progress bar and `decoder.isComplete` for completion. [Automatic format routing](https://github.com/Egge21M/nut-fountain/blob/c18459671c0412dd3be0192f4b45e689d545cffb/packages/nut-fountain/docs/implementation.md#automatic-format-routing).
4. `tokenToBytes(cashuB)` converts to compact `crawB` bytes while preserving the token's original CBOR; `bytesToTokenString()` restores unpadded `cashuB`. The helpers do not support `cashuA`. The raw core and UR adapter transport arbitrary bytes, so legacy `cashuA` text can remain supported through explicit UTF-8 handling and existing token parsing. Avoid sending all legacy UR results unconditionally through the V4-only helper. [Cashu conversion rules](https://github.com/Egge21M/nut-fountain/blob/c18459671c0412dd3be0192f4b45e689d545cffb/packages/nut-fountain/docs/implementation.md#cashu-conversion-and-encoding-helpers).

## Compatibility and operational limits

- **Incoming legacy UR:** The adapter supports `ur:bytes` with a CBOR byte-string payload, uppercase input, single-part and multipart messages, and repair frames. Cashu.me's current sender uses that wrapper around token text. The adapter is not a claim of compatibility with every wallet's payload conventions. [UR adapter](https://github.com/Egge21M/nut-fountain/blob/c18459671c0412dd3be0192f4b45e689d545cffb/packages/nut-fountain/docs/implementation.md#inbound-ur-compatibility).
- **Outgoing compatibility:** Removing the UR encoder removes the ability to emit animated transfers to UR-only wallets. A compatibility option would require retaining a UR encoder. Keep this decision separate from whether the new format works technically. [Package entry points](https://github.com/Egge21M/nut-fountain/tree/c18459671c0412dd3be0192f4b45e689d545cffb/packages/nut-fountain), [NUT-16](https://github.com/cashubtc/nuts/blob/main/16.md).
- **Session lifecycle:** Binary malformed/foreign frames throw; invalid UR parts generally return `false`. A selected `AutoDecoder` throws if another recognized format arrives. Catch errors in the scan callback and provide reset/restart behavior when changing transfers. `receive()` returning `true` does not mean completion. [Decoder state and errors](https://github.com/Egge21M/nut-fountain/blob/c18459671c0412dd3be0192f4b45e689d545cffb/packages/nut-fountain/docs/implementation.md#decoder-state-progress-and-errors).
- **Capacity:** At most 1024 source fragments and 1 MiB overall. A 232-byte fragment setting supports at most 237,568 message bytes; 256 supports 262,144. These limits concern decoded message bytes, not the longer base64 token text. [Protocol bounds](https://github.com/Egge21M/nut-fountain/blob/c18459671c0412dd3be0192f4b45e689d545cffb/packages/nut-fountain/docs/protocol.md#2-version-1-bounds-and-fragmentation).
- **Browser/build fit:** ESM, modern browser bundlers, native `BigInt`, Node 22.4+. Published dependencies include cashu-ts 4.11.0, cborg 4.3.2, and noble/hashes 2.4.0. Cashu.me already declares Node >=22.4 and cashu-ts ^4.9.0. Use scoped `core`/`auto` imports if existing Cashu serialization is retained; these avoid pulling Cashu helpers into that import path. [Published metadata](https://registry.npmjs.org/nut-fountain/0.1.0), [package documentation](https://github.com/Egge21M/nut-fountain/tree/c18459671c0412dd3be0192f4b45e689d545cffb/packages/nut-fountain).
- **Maturity/performance:** This is an explicitly experimental 0.1.0 release whose API and wire compatibility may change. Upstream reports Chromium library tests, including loss, reordering, duplicates, repair-only reconstruction, and UR fixtures; it explicitly excludes real-wallet/QR-reader performance and other browser engines from its acceptance run. A 20 FPS setting is feasible, but reliable device throughput remains to be measured. [Validation record](https://github.com/Egge21M/nut-fountain/blob/c18459671c0412dd3be0192f4b45e689d545cffb/packages/nut-fountain/docs/validation.md).

## Local feasibility checks

An isolated Node test in `/tmp/cashu-fountain-check/check.mjs` used the published packages without changing this project's dependencies:

- Encoded a synthetic, non-spendable 12-proof V4 token with `nut-fountain@0.1.0`, rendered binary PNG QR codes with `qrcode@1.5.3`, scanned them using the project's underlying `zxing-wasm@2.2.4`, and reconstructed the exact token string with `AutoDecoder`.
- Repeated this with fragment sizes 232 and 256, verifying exactly 256 and 280 bytes per QR payload respectively. Dropped every third generated frame, including source frames; both transfers completed using repair frames. These are small synthetic cases, not a throughput benchmark.
- Generated uppercase UR parts using the existing `@gandlaf21/bc-ur@1.1.12` ESM implementation and verified exact payload recovery through `AutoDecoder` for a V4 token and a synthetic `cashuA`-prefixed transport string. The latter checks opaque text preservation, not V3 token validity or redemption. The old package's CommonJS entry could not load its ESM-only cborg dependency in Node, so its browser-oriented ESM entry was bundled for this check.

These checks establish binary QR and legacy UR transport feasibility. They do not exercise the current text-only scanner wrapper, Vue integration, a live camera, or 20 FPS rendering.

## Validation needed before rollout

Verify binary QR rendering/scanning preserves every byte, compare reconstructed token strings exactly, test missing/duplicate/out-of-order frames and legacy UR, and exercise malformed input and transfer reset. Then run real camera transfers on desktop, Android, and iOS at the requested defaults. Confirm whether outbound support for UR-only wallets must remain. These checks separate basic protocol integration from real-device reliability.
